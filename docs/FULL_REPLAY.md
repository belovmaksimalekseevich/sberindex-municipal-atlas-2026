# Полное воспроизведение расчёта

В опубликованном пакете есть входные данные, научный код и 532 сохранённых результата. Их можно проверить без обучения за несколько секунд. Полное воспроизведение запускает расчёты заново: 504 месячных разбиения и 28 разбиений годового контекста. Это отдельный, длительный режим.

Ниже команды выполняются из корня клона. Научный каталог `research/` не изменяется. Виртуальное окружение, результаты и квитанции создаются снаружи репозитория; пути в командах заключены в кавычки.

## Сначала — проверка сохранённого пакета

Достаточно Python 3.11 и стандартной библиотеки:

```bash
python3.11 -B -S research/release.py verify
python3.11 -B -S research/code/typology.py show --month 2024-12 --method NCut --k 10
```

Это проверяет комплектность и контрольные суммы опубликованных файлов и читает уже сохранённый результат. Успешная проверка не означает, что новый полный расчёт выполнен.

## Машина и окружение

Для полного расчёта нужен Linux с Python **3.11**, доступными логическими CPU **0 и 7** и точными версиями из [requirements-compute.txt](../research/code/requirements-compute.txt). Само наличие восьми CPU не гарантирует доступ к номерам 0 и 7: контейнер или планировщик может разрешить другой набор. Номера заданы в принятом контроллере и автоматически не переназначаются.

Рекомендуется 8 vCPU, 16 GiB RAM и не менее 32 GiB свободного диска после установки окружения. Жёсткий порог контроллера — 12 GiB свободного диска; предел выборочного измерения памяти дерева процессов — 4 GiB. Это ограничения допуска, а не гарантия длительности или отсутствия кратких пиков памяти. Для контейнера отдельно проверьте его лимит RAM: доступная память хоста не равна выделенной контейнеру.

Должны работать Linux `pidfd_open`, `pidfd_send_signal` и `prctl` для контроля дочерних процессов. Предварительная команда проверяет открытие pidfd, сигнал 0 и чтение состояния subreaper. Разрешение менять subreaper окончательно проверяет сам контроллер. При ограничениях seccomp или недостаточных правах расчёт может остановиться до первого этапа.

На системе, где команда `python3.11` отсутствует, сначала установите Python 3.11 средствами вашего дистрибутива. Замена его на системный Python другой версии не входит в проверенный режим.

```bash
python3.11 --version
mkdir -p "$HOME/sberindex-replay"
python3.11 -m venv "$HOME/sberindex-replay/venv"
PY="$HOME/sberindex-replay/venv/bin/python"
"$PY" -m pip install -r research/code/requirements-compute.txt

OUT="$HOME/sberindex-replay/run-$(date -u +%Y%m%dT%H%M%SZ)"
"$PY" -B scripts/full-fit-check.py preflight --out "$OUT" \
  --receipt "${OUT}.preflight.json"
"$PY" -B -S research/code/typology.py plan --out "$OUT"
```

`PREFLIGHT_PASS` означает, что текущие версии, доступные CPU, базовые возможности Linux, свободное место и память удовлетворяют проверкам. Команда ничего не обучает, не создаёт `OUT` и не резервирует CPU. Перед запуском освободите CPU 0 и 7 от конкурирующих заданий. После неуспешного preflight не продолжайте автоматически: устраните указанную причину и выберите новое имя квитанции.

## Запуск

Выделите до пяти часов на очередь расчётов и ещё час на проверку и копирование результата. Прежний полный контроль занял около 9416 секунд; это измерение одной машины, не обещание для нового оборудования.

Для удалённой Linux-машины запускайте команды в устойчивой терминальной сессии, например `tmux`. Сначала войдите в неё, затем заново задайте `PY` и `OUT` из предыдущего блока. Закрытие подключения не должно отправлять контроллеру SIGHUP. Жёсткое завершение процесса или выключение машины не считается корректной остановкой и требует отдельной проверки оставшихся процессов.

После успешного preflight:

```bash
"$PY" -B research/release.py full-fit --out "$OUT" \
  --allow-real-fitting --exclusive-cpus-confirmed
```

`--exclusive-cpus-confirmed` — ваше подтверждение выделения CPU, не действие по их резервированию. Контроллер последовательно выполняет 25 месячных заданий, включая январский пилот, и один блок из 28 контекстных разбиений. Январский основной этап использует разрешённый кэш пилота. Повторного обучения пилота внутри этого этапа нет.

Папка `OUT` должна быть новой. Автоматических повторов и продолжения частичного результата нет. Основной статус — `OUT/RECEIPT.json`, журналы — `OUT/logs/`. `HELD`, отсутствующий финальный статус или ненулевой код завершения означают незавершённый запуск. Сохраните каталог для диагностики; не выдавайте его за полный результат и не запускайте вторую копию поверх него.

## Проверка завершённого результата

После возврата команды запуска с кодом 0, **на той же Linux-машине, в том же PID namespace и до перезагрузки**:

```bash
"$PY" -B -S scripts/full-fit-check.py check --out "$OUT" --live-owners \
  --receipt "${OUT}.check.json"
```

Проверка работает стандартной библиотекой. Она читает каталог и ничего в нём не исправляет. Проверяются:

- завершённые квитанции всех 26 этапов и сохранённые подтверждения очистки процессов;
- точная сетка 504 + 28 без лишних или отсутствующих ячеек;
- манифесты и SHA файлов каждого этапа, 3721 закрытая пара вызовов и 2688 зарегистрированных входов Lloyd месячной части;
- исходные задачи и seeds, версии окружения в контекстной квитанции, порядок и состав ID;
- состав групп с допустимым взаимно однозначным переименованием номеров, размеры групп, индивидуальные SW и все поля метрик, включённые в публичную сохранённую проекцию;
- при `--live-owners` — отсутствие записанных PID с теми же `boot_id` и `start_ticks`, включая зомби.

Код 0 и `READBACK_AND_RECORDED_OWNERS_PASS` подтверждают эти проверки. Совпадение `boot_id` проверяется автоматически; тот же PID namespace должен обеспечить оператор (не запускайте проверку в другом контейнере). Проверка известных PID не заменяет общий обзор заданий оператора и не устанавливает научную полезность модели. Файл `RECEIPT.json` и внутренние манифесты не являются цифровой подписью того, какой процесс реально исполнялся.

Для уже перенесённого каталога, например на Windows, уберите `--live-owners`. Успешный статус будет **`READBACK_PASS`**. Он подтверждает сохранённые данные и квитанции, но не текущую очистку процессов на исходной машине. На другой машине или после перезагрузки `--live-owners` намеренно отказывает.

Числа сравниваются по ранее принятому правилу:

```text
abs(a - b) <= 2e-11 + 2e-10 * max(abs(a), abs(b))
```

Это допуск для конечных чисел с плавающей точкой. Типы, статусы метрик, причины неопределённости, идентификаторы и составы групп сравниваются точно. Правило отражено в опубликованной [квитанции принятого воспроизведения](../research/code/provenance/replay_parity.json), поле `float_rule`. Допуск не подбирается по новому результату. Прежняя квитанция требовала также одинаковых сырых номеров групп; новый переносимый checker разрешает только взаимно однозначное переименование при одинаковом членстве. Это явно более переносимое правило для номеров, а не разрешение «почти совпадающего» разбиения.

Проверяется **публичная компактная проекция 532 результатов**. Прежняя более широкая проверка 897 нативных записей здесь не воспроизводится. Не пересчитываются матрицы графов, собственные векторы или формулы индексов из первичных данных. Успех переносимого checker не равен побайтовой идентичности всех численных промежуточных файлов между Linux и Windows.

## Чтение архивного контроля

Если у вас есть сохранённый архив полного контроля с каталогом `compute/`, его можно проверить без распаковки:

```bash
python3.11 -B -S scripts/full-fit-check.py check \
  --archive /external/final_control_run.zip --prefix compute/ \
  --receipt /external/archive-readback.json
```

Указанный архив не требуется скачивать для обычного воспроизведения: новый результат создаёт команда `full-fit`. Архивный режим проверяет записанный контроль и не доказывает новый запуск. Для квитанции вычисляется SHA всего ZIP; это может занять несколько минут вместе с чтением файлов. Если у вас есть SHA из независимой доверенной квитанции, передайте его параметром `--expected-sha256`. Без этого параметра SHA служит идентификатором прочитанного архива, а не подтверждением его происхождения.

## Что подтверждено при выпуске этой инструкции

Чтение и экспорт сохранённых результатов проверены из свежего публичного клона без научных зависимостей. Команда проверки прошла **ранее принятый полный архив** без повторного обучения; отдельные тесты проверяют отказы на повреждённых файлах, неверных типах и изменённом составе групп. Новый полный запуск по этой инструкции на чистой Linux-машине пока не выполнялся. Научный код, входы и манифесты `research/` при добавлении этих команд не менялись.

Для небольшого эксперимента с другими параметрами используйте отдельный [режим JSON-конфигураций](../experiments/README.md). Его результат не подменяет принятую сетку, опубликованные группы или описанный выше полный контроль.
